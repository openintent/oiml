# Design: audit entries, and webhooks to other systems

**Status: proposed 2026-11-09.** Not yet built. Two side effects of operations the model already knows, declared
once instead of placed by hand at every call site. The grammar below is the design to review before the build.

Both applications surveyed for these notes record who changed what. One does it through declarative catalogs per
entity (field, label, kind) read by an audited procedure wrapper inside the transaction, with a walk that fails a
mutation under a covered router that forgot to declare its audit; the other has sixty-one hand-placed log calls.
Both deliver events to other systems: one through a transactional outbox with declared topics and payload schemas
and docs generated by a snapshot test, the other through a dispatcher with a wildcard family per event, HMAC
signatures, a fetch that refuses private addresses, and its own retry schedule, called from nine files. OSL has the
operations, the rows, the actor and a job queue; what is missing is the declaration.

## What was asked

No round has asked for either yet: the generated intents stay inside one application, and "history, versions and
audit" is a topic in the gap clustering with no entry until now. The asks below are the ones the hand-written
applications answered, in the order they met them.

| Ask                                                                      | Verdict                             |
| ------------------------------------------------------------------------ | ----------------------------------- |
| Who changed what on this row, and when, shown on the row                 | construct: `audit`                  |
| An admin reviewing what a user changed across an account                 | construct, through the audit entity |
| Another system told when a row is created, closed or deleted             | construct: `webhooks`               |
| A customer registering a URL and verifying the signature of what arrives | construct                           |
| Undoing the last change                                                  | not a construct; the audit shows it |

## 1. Audit

```yaml
entities:
  Ticket:
    audit: true # or { rule: "role:admin" }: who may read the entries; default the entity's read rule
```

A compiler-added entity `AuditEntry` (`entity`, `row_id`, `operation`, `actor_id` → identity nullable, `at`,
`changes` json) receives one row, in the same transaction, for every create, update, delete, action, transition,
archive and restore on an audited entity, also when a schedule or timer runs it (`actor_id` null, `operation`
naming the schedule). `changes` holds `{ <field>: [before, after] }` for updates and the row for creates and
deletes, as the API presents it: hidden, sealed and `read`-ruled fields never appear, so the audit cannot leak what
the API would not. `GET /api/tickets/{id}/audit` lists entries newest first under the rule; the detail pane gains a
History section; scenarios call `tickets.audit`.

## 2. Webhooks

```yaml
webhooks:
  events: [Ticket.created, tickets.close, Comment.deleted] # the events endpoints may subscribe to; the events grammar
  rule: "role:admin" # who manages endpoints; default role:admin, else authenticated
```

- A resource `/api/webhooks` over a compiler-added `WebhookEndpoint` (`url`, `events` array, `secret` sealed and
  hidden, shown once in the create reply, `active`, `created_by`) under the rule, with a `rotate_secret` action.
  The URL is refused at create and at delivery when it resolves to a loopback, link-local or private address.
- A compiler-added `WebhookDelivery` (`endpoint_id`, `event`, `payload`, `attempts`, `status`, `last_status`,
  `next_at`) and `GET /api/webhooks/{id}/deliveries` under the same rule, with a `redeliver` action.
- Dispatch: each listed event enqueues one job per active endpoint subscribed to it on the queue the backends have
  (pg-boss, River), delivered as `POST url` with `{ id, event, at, data }` where `data` is the row as the API
  presents it to the system (hidden, sealed and `read`-ruled fields left out), headers `X-OSL-Event`,
  `X-OSL-Delivery` (the id, for idempotence) and `X-OSL-Signature` (HMAC-SHA256 of the body, `t=<unix>,v1=<hex>`),
  a 10 second deadline, five attempts with exponential backoff, then `failed`.
- Under the test hooks, an endpoint may point at `{hooks}/webhooks/receive` and `webhooks.sent` lists what arrived,
  with the signature verified by the hook; `emails.sent` has the same shape.
- OpenAPI gains a `webhooks` section with one entry per event and its payload schema; the generated README shows
  how to verify a signature in three lines.

## Mapping

- Core: `Entity.audit?: true | { rule }`, top-level `webhooks: { events, rule }`; the IR adds the two entities,
  their resources and the audit routes, and marks every mutating operation of an audited entity `audited: true`.
  Diagnostics: an audited entity that is the audit entity, a webhook event not in the events grammar or naming an
  action of a resource that does not exist, a declared entity or resource named like the compiler-added ones.
- drizzle-next and hono-trpc-vite: the resource module writes the audit row through a shared `recordAudit(tx,
...)` after the write and before commit, using the presenter so the field exclusions hold; the dispatcher is a
  queued-event handler the compiler writes, with the signing and the address check in `@osl/ts-common`; the pages
  render History and the Webhooks admin page (an ordinary resource page over the compiler-added resource).
- gin-pgx: the same in the resources and jobs packages; `crypto/hmac`, `net` for the address check.
- Diff: `set_audit { entity, audit }` and `set_webhooks { webhooks }` / `remove_webhooks`.
- Reference: a paragraph under Entity and a section after Events, and the rules for choosing: "who changed what"
  is `audit`; "tell another system" is `webhooks`; "notify a user" is an event handler and the email adapter.

## Declined, with the sentence the reference gets

- Undo and restore from audit: "the audit shows the change; restoring is an update".
- Audit of reads: "reads are not audited".
- Per-endpoint event filters beyond the list (by field value): "an endpoint subscribes to events; filter on
  receipt".
- Incoming webhooks from other systems: a custom route in `src/`; the model describes this app's API.
- Delivery to a queue or an email instead of a URL: a URL is the contract.

## Proof

- Fixtures: workspace WS-14 "ticket history and integrations": `Ticket` with `audit: true` and a scenario that
  creates, updates twice, closes (a declared action), and reads `tickets.audit` expecting four entries with the
  right actors, operations and a `changes` entry showing before and after for the title, and no `budget` (a
  `read`-ruled field) in any entry; `webhooks` over `Ticket.created` and `tickets.close`, the admin creates an
  endpoint at the capture URL (201 with the secret once), a member cannot (403), a ticket is created and closed,
  `webhooks.sent` shows two deliveries with verified signatures, a private-address URL is refused (400), and
  `GET /api/webhooks/{id}/deliveries` lists both as delivered. A second endpoint at a closed port shows one
  failed attempt in its deliveries after the hook runs the queue once; the retry schedule itself is a unit test on
  the dispatcher, since the scenario clock does not drive the queue's backoff.
- Eval cases: `fx-ws-14-ticket-history`, and the r6 external-notification ask promoted.
- Gate: as every round, then `built` for "history, versions and audit" and "webhooks to other systems".

## Size

Core: two keys, two compiler-added entities with resources, the audited marks, four diagnostics, two diff ops, the
reference. A shared audit writer and a dispatcher per backend, the History section and the Webhooks page in the
two web backends, two hook routes. About the size of the scheduling round.
